# 提示词设计说明

> 这个项目的"技术含量"主要不在 CRUD，而在这几个提示词怎么设计、以及围绕它们做了哪些工程约束。
> 所有提示词常量集中在 `backend/app/services/prompts.py`。

## 1. 六类模型调用

| 任务 | 输出形态 | 温度 | 可以用便宜模型 | 说明 |
|---|---|---|---|---|
| `resume_parse` 简历结构化 | JSON | 0.1 | ✅ | 纯抽取，越低越稳 |
| `jd_parse` 能力模型 | JSON | 0.2 | ✅ | 需要权重归一化 |
| `match` 匹配分析 | JSON | 0.2 | ✅ | 结论 + 依据 |
| `plan` 面试计划 | JSON | 0.4 | ⭕ | 需要一点创造性来设计考察点 |
| `interviewer` 面试官话术 | **纯文本、流式** | 0.7 | ❌ | 要像真人，但要短 |
| `evaluator` 单题评分 | JSON | 0.2 | ✅ | 必须独立于出题 |
| `report` 复盘报告 | JSON | 0.3 | ✅ | 结构化要求最强 |

## 2. 面试官提示词：为什么最终输出纯文本

### 2.1 走过的弯路

第一版让面试官输出 JSON：

```json
{"say": "...", "question": "...", "is_followup": true, "competency": "...", "stage_finished": false}
```

问题立刻暴露：**JSON 不能边生成边用**。你必须等整段（含所有字段）生成完才能解析，
于是前端的"流式打字机"只能退化成"等 3 秒然后一次性出现"。

同时，把"要不要追问"交给模型判断，会导致追问层数失控——模型会围绕第一个项目连续追问到面试结束。

### 2.2 现在的方案

把这一轮拆成两件事：

```
[服务端 · 确定性]  decide_next()  ──►  本轮动作：intent + stage + competency + 追问层数
                                              │
[LLM · 流式纯文本] ◄──────────────────────────┘
   输入：动作类型 + 考察点 + 可追问方向 + 对话记录 + 时间进度
   输出：面试官这一轮说的话（≤120 字，纯文本）
```

面试官提示词里明确写了：

> 你**只负责把这一轮要说的话说出来**，面试环节和考察点已经由系统决定好了，你不需要自己规划面试流程。

好处是双向的：
- 追问逻辑变成可单测的纯函数（`test_interview_engine.py` 有 29 项断言）；
- 面试官输出可以直接流式吐给浏览器；
- 模型跑偏的后果被限制在"话说得不自然"，不会破坏面试结构。

### 2.3 风格约束的写法

约束要写成**可判定的否定式**，而不是"要专业"这种形容词：

| ❌ 无效约束 | ✅ 有效约束 |
|---|---|
| 要专业、要简洁 | 总长度不超过 120 字；最多一句衔接语 + 一个问题 |
| 不要啰嗦 | 不点评候选人的回答（不得出现"这个回答不错"） |
| 要追问细节 | 追问时必须**引用候选人原话里的具体内容** |
| 输出格式正确 | 直接开口说话，不要"面试官："前缀，不要引号包裹，不要 markdown |

## 3. 追问规则：把它写成代码，不是写成提示词

三条规则实现在 `interview_engine._followup_intent()`：

```python
1. 回答里有具体数字 / 技术名词 / 量化成果  →  INTENT_FOLLOWUP_DETAIL
   （问：怎么做的？为什么这么选？数据怎么来的？）

2. 回答空泛（出现"参与了""做了一些""提升比较明显"且没有数字/技术细节）
                                          →  INTENT_FOLLOWUP_CONCRETE
   （问：举一个具体场景，你具体做了什么改动？）

3. 压力环节，或"有数字 + 有对比"的强主张    →  INTENT_FOLLOWUP_CHALLENGE
   （问：这个结论在什么条件下会不成立？）
```

外加两条硬约束：

- **同一考察点最多追 2 层**（`MAX_FOLLOWUP_DEPTH = 2`），之后强制换考察点；
- **剩余时间低于 20% 时停止追问**，低于 5% 直接进入反问收尾。

这些都是纯字符串规则（`analyze_answer()`），零模型调用、零成本、完全确定。

> 面试里可以这样讲：**我把提示词里"请适当追问"这种模糊指令，换成了可断言的规则，
> 并用 29 个单测覆盖了它的边界（2 层上限、时间耗尽、开场不追问、反问环节不追问）。**

## 4. 评分提示词：四个防偏置设计

### 4.1 角色隔离

```
你是一名严格但公正的校招面试评估专家。
你**不是**出题人，你只对候选人这一轮的回答打分量。
```

出题与评分是两次独立调用、不同温度、可以是不同模型。避免"自己给自己出题打高分"。

### 4.2 固定锚点

5 分制每一档都给了可操作的定义，而不是"很好/较好/一般"：

```
5 = 有具体数据、有取舍权衡、有反例或反思，可直接通过校招该轮
4 = 完整清晰、技术正确，但缺少权衡或量化
3 = 基本答对、偏教科书、缺个人实践细节
2 = 答非所问或明显错误，但方向、态度尚可
1 = 空泛套话、无法判断，或答错且不自知
```

并显式要求 **"不要都给 3 分——请拉开区分度"**（模型有强烈的居中倾向）。

### 4.3 强制证据引用

```
`evidence` 必须**逐字引用候选人原话**（2-4 条）。
严禁写"他的回答比较空泛"这种无引用的判断。
```

这一条同时解决了两个问题：分数可解释，以及**防止模型凭印象打分**——
它必须先找到原话，才能给分。

### 4.4 改写示范的伦理边界

```
`rewritten_answer`：把候选人的回答改写成一段高分示范（150-250 字）。
**只能基于他真实说过的经历改写**……**严禁新增他没提过的项目、数据或经历**。
```

没有这条约束，模型会顺手编造"我把 QPS 提升到 5000"这类漂亮但不存在的成绩——
那会教学生编简历，是这个产品最不能做的事。

## 4.5 面试官人格注入：只改"怎么问"和"看重什么"

第二轮迭代新增了 6 位面试官人格（HR / 技术主管 / 技术专家 / HRBP / 架构师 / 终面面试官）。
人格会注入**两处**提示词：

| 注入点 | 函数 | 效果 |
|---|---|---|
| 提问提示词 | `build_question_system(persona)` | 决定用什么口吻问、怎么追问、对什么回答不满意 |
| 评分提示词 | `build_evaluator_system(persona)` | 决定五维分数的**侧重** |

第二处容易被漏掉。如果只改提问不改评分，就会出现错位：
架构师在问方案权衡，评分却在看你有没有讲清求职动机。

但注入时必须**加一条边界**，否则模型会滥用"我是 HR"这个身份：

```
【本轮的面试官是谁（据此调整评分侧重）】
你是 李雯，校招 HR。……
注意：人格只改变**五维分数的侧重**，不改变评分维度本身，也不改变锚点标准。
```

人格**不注入**决策层 —— 该追问还是该换考察点，仍然由 `interview_engine.decide_next()` 这个
纯函数决定。人格只影响"措辞"和"侧重"，不影响"结构"。

**换人时要自报身份。** 多轮模式下换面试官，提示词里会加上：

```
【注意：本轮换人了】请用**一句话**自报身份再提问（例如「我是陈刚，接下来聊聊你的项目部分」）。
不要长篇自我介绍，不要寒暄，不要解释为什么换人。
```

不加这一条，考生会以为面试官人格分裂。

实现：`prompts.py::build_question_system / build_evaluator_system` ·
`interview_service.py::build_question_context`（检测 `previous_interviewer != current`）

## 4.6 把"表达流畅"变成可核对的数字

这是全项目里**最容易被模型糊弄过去**的维度。

原始问题：模型读一段文字，既听不出你语速多快，也听不出你卡了几次。
于是 `delivery` 只能凭文本长度猜 —— 这等于没评。

第二轮的做法：视频/语音作答时，前端从 **ASR 结果 + 录音时间轴**算出客观指标随回答上报，
评分提示词里写死判定口径：

```
【作答方式】语音作答（ASR 转写），以下为录音实测的客观指标，**请以此为准**：
- 回答时长：61 秒
- 字数：210
- 语速：207 字/分钟（正常区间 180-320）
- 口头禅：12 次，占比 7.1%（低于 2% 算干净）
- 长停顿（>2.5 秒）：2 次，最长 3.4 秒

【关于「表达」维度的评分纪律】
- 语速低于 180 字/分钟 → 像背稿或思路不清，最高 3.5 分
- 语速高于 320 字/分钟 → 像赶时间，最高 3.5 分
- 口头禅占比超过 6%   → 明显影响听感，最高 3 分
- 长停顿超过 3 次     → 卡壳明显，最高 3 分
```

**关键的反面设计**：纯文字作答时，明确告诉模型**没有数据**：

```
【作答方式】纯文字输入，无可用的语速/停顿数据。**不要臆测语速或停顿。**
```

不写这一句，模型会为了"显得在认真评分"而编一个语速出来 ——
这和编造成绩是同一类错误。

实现：`prompts.py::render_delivery_metrics` · `frontend/src/lib/deliveryMetrics.ts`
（前后端阈值必须一致：180-320 字/分、2.5 秒长停顿、`FILLER_WORDS` 词表）

## 4.7 参考答案的"占位符纪律"

考生点"看参考答案"时，最大的风险是：模型顺手编造漂亮但不存在的成绩。
那等于教学生编简历 —— 是这个产品最不能做的事。

所以提示词的第一条不是"怎么写好答案"，而是：

```
【最重要的规则：不要编造】
- 你只能使用候选人**自己提供的**事实：简历要点、他刚才的回答、岗位 JD。
- **缺少关键事实时，必须保留占位符，绝不允许猜测或填补**。
  占位符写成方括号形式，例如：`[补充你的具体指标，如 QPS 或耗时]`、
  `[补充你在该项目中的具体职责]`、`[补充对比基线]`。
- 宁可留下一个占位符，也不要编一个漂亮的数字。编造数据会让他在真实面试中被当场问穿。
```

并且把占位符单独抽成 `placeholders: string[]` 字段返回，
前端用琥珀色框高亮"这些地方需要你补上真实数据（AI 不会替你编）"。

生成结果**缓存进 `Turn.suggested_answer`**：同一题永远只花一次模型调用，
重复点击直接返回缓存。

## 4.8 反 AI 腔护栏

视频面试里"对面是不是人"这件事比文字面试更敏感，所以第二轮专门加了一组否定式约束：

```
【你必须像一个真人面试官，而不是 AI 助手】——这几条比任何风格描述都重要
- **不要用 emoji**，不要用"首先/其次/最后"这类书面连接词，不要模板化寒暄。
- **绝不要质疑候选人提到的技术、工具或公司是否真实存在**。哪怕他说了一个你没听过的名词，
  也要当作正常技术去追问细节，而不是反问"这是什么"。装懂会立刻暴露你不是人类。
- 不要说"作为一个 AI""根据我的理解"这类话，不要道歉，不要解释你的提问意图。
- 候选人答不上来时**不要安慰他、不要说"没关系"**，可以停顿一下换个角度再问一次。
```

第二条最值得说：AI 面试官有一个很典型的破绽 —— 考生提到一个冷门技术，
模型会反问"这是什么？"。真人面试官不会这么干，那等于承认自己不懂行。
所以要在提示词里**明确禁止模型"装懂式反问"**。

第四条同样反直觉但正确：安慰是 AI 的默认行为，而真实面试官不会在你说不会的时候说"没关系"。

## 5. 报告提示词：反套话设计
通用大模型写复盘报告时，最容易产出这种没信息量的东西：

> 总体表现良好，建议继续努力，加强技术深度和表达能力的训练。

所以报告提示词里写满了禁令和硬性要求：

| 要求 | 目的 |
|---|---|
| `summary` 必须点名 **2 个具体优点 + 2 个具体短板**，各引用本场内容 | 逼它说具体的事 |
| 严禁"表现良好，还需努力""总体不错" | 直接封掉套话 |
| `top_problems` **最多 3 条**，按严重程度排序 | 聚焦，改 3 个就够 |
| 每条必须含 `evidence`（逐字原话）+ `why_bad`（面试官视角后果）+ `how_to_fix`（具体动作）+ `demo_answer` | 从"诊断"闭环到"怎么改" |
| 训练计划 **7 天、每天恰好 1 个任务**，必须具体到"练什么题/写什么文档/背什么话术" | 可执行 |
| **严禁**"多看书""多练习""多刷题""加强学习" | 这类任务等于没有任务 |
| `verdict` 四档，对齐真实校招标准，不要普遍给 `pass` | 防止一致性偏松 |

E2E 脚本里有一条断言专门检查训练计划不含上述空话词。

## 6. 合规红线（写进每一处提示词）

```
【合规红线】绝不询问、推断或评价候选人的年龄、性别、婚育状况、籍贯、民族、
宗教信仰、健康状况、家庭背景、外貌或口音。若输入材料中包含此类信息，
一律忽略，不得在提问或评分中体现。
```

- 面试官提示词：不问、不推断；
- 评分提示词：评价表达时只能使用中性的"清晰度"表述，不得评价口音、外貌；
- 评分维度里**根本没有**"形象""气质"这类项——不是靠提示词劝阻，而是结构上不存在。

## 7. 可迭代性

提示词全部是模块级常量 + 纯函数式的上下文渲染函数（`*_user()`），
改提示词不需要动任何业务逻辑。想对比两版提示词的效果，只需要替换常量并重跑
`scripts/e2e_check.py`。

## 8. 还没做但应该做的

**评分一致性评估**。当前所有防偏置手段都是"设计上应该有效"，但没有实测数据。
正确的做法是：取 20 份真实问答，人工按同一 rubric 打分，
计算 AI 分与人工分的 Spearman 相关系数，并统计各维度的系统性偏差（偏松/偏严）。
这件事写进了 README 的「后续规划」，也是这份项目最该补的一块。
